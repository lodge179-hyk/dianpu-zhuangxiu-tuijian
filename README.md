# AI 店铺装修设计（代表性案例 Demo）

一个不懂设计的商家，上传一张店铺截图，得到：**AI 定的装修方案（调性/模块/顺序/每张图画什么）+ 固定模块渲染的完整预览 + 可下载的独立素材与装修清单**。

- 工程目录：`H:\dianpu-ai-design`（独立工程、独立依赖、独立端口，不共享原工作区）
- 入口：<http://127.0.0.1:5191/>
- 启动：`npm start`（等价于 `node --env-file-if-exists=.env.local server.mjs`）
- 自检（不调用模型）：`node selfcheck.mjs`
- 样例渲染（不调用模型）：`node render-sample.mjs` → `output/sample-render/preview.html`

## 一、这一轮验证什么

> AI 能不能为**这家店**选出有理由、适合它的模块与素材组合。

因此流程里刻意把「决策」与「呈现」分开：

| 环节 | 谁负责 | 实现位置 |
| --- | --- | --- |
| 看懂店铺（品类、可见商品、内容信号、调性） | AI | `src/analyze.mjs` |
| 决定风格、选模块、排顺序、给理由、规划图片用途 | AI | `src/plan.mjs` |
| 画布尺寸、面板比例、分隔色、提示词措辞、裁切、缩放、排版、导出 | 程序 | `src/assets.mjs`、`src/render.mjs` |
| 生成组合素材图 | 生图模型 | `src/assets.mjs` |
| 固定 UI 与页面骨架 | 冻结组件库 | `vendor-component-library/` |

## 二、模块库是封闭的（借鉴 json-render 的 catalog 做法）

`src/catalog.mjs` 从冻结组件库**自动提取**可选模块目录，AI 只能在这 23 种里选：

- 店铺招牌 4 种 · 分类导航 2 种 · 图片海报 7 种 · 轮播图 3 种 · 商品橱窗 4 种 · 公告与文本 3 种
- 共 **55 个图片槽位**，每个槽位的真实宽高比来自实测数据（例如导航圆形图标 71.27px、三列海报方形槽位 160.33px、中图轮播 483×362.25 即 4:3、橱窗商品图 147.66px 方形）
- 目录同时用于两件事：**生成给 AI 的系统提示词**，以及**校验 AI 的计划**

`src/validate.mjs` 在任何生图之前拦下不合法的计划：模块不存在、图片张数与槽位不符、来源不是四种之一、槽位重复使用、招牌不在首位、极简招牌带自定义背景、三列橱窗商品数不是 3 的倍数、价格不是纯数字……自检里 8 类坏计划全部被拦下。

## 三、生图只花在必须生成的地方

每张图必须归入四种来源之一，由 AI 判断：

| 来源 | 处理方式 |
| --- | --- |
| `product-photo` | **不生成**，从商家截图按识别到的商品位置裁切，避免把商品画错 |
| `generated-scene` | 生图（招牌横幅、氛围场景） |
| `generated-nav-icon` | 生图（简洁扁平图标，不含文字） |
| `generated-poster` | 生图（有构图的海报，不含文字） |

所有需要生成的图**合并到尽量少的画布**上（AI 决定哪几个格子放一起，程序按槽位真实比例排版）：

- 画布用纯品红 `#FF00FF` 做外边距与格子间隔，程序按品红投影切出面板
- 面板比例严格等于槽位比例，裁切只做最小中心裁切（超过 25% 直接拒绝，不硬裁）
- 残留分隔色逐像素检测，非零即记录
- 放大倍数如实记录（每个槽位按原生尺寸的 2 倍输出，放大超过 1.02 倍会标注）

## 四、已实现

- 单入口单端口：上传一次 → 得到方案、预览、素材，中途不需要任何设计输入。
- 六步流程状态可见：规范化截图 → 看懂店铺 → 装修决策 → 生成并裁切 → 渲染整页 → 打包清单。
- 计划校验前置：不合法就在生图前停下，不会带着错误计划去花钱。
- 缺图/生图失败**只降级不终止**：用带「图片缺失」标注的占位图保持布局，并在界面上写明。
- 装修清单 `manifest.json`：模块顺序、每个模块的理由、每个图片位对应哪个文件、该文件属于哪个来源、页面坐标、原生像素与交付像素。
- 界面直接展示 AI 的决策与理由（招牌/主视觉/陈列/顺序各自为什么这么选），以及 AI 自述的信息缺口。
- 费用保护：提交接口要求显式 `confirm=1`，未确认返回 428 且不调用任何模型。

## 五、已知限制

- **生成图是装修示意图，不是商家真实商品的精准还原。** 截图里的商品通常很小，识别与裁切都受限于截图清晰度；`product-photo` 槽位的素材来自截图裁切并如实标注是否取得精确位置。
- 商品数量与内容以 AI 识别到的可见商品为准，识别不到就不编造；价格只在截图确实有可靠来源时才写。
- 图片槽位按原生尺寸的 2 倍输出（例如 147.66px 槽位输出 296×296）。截图本身商品区域很小时，这个尺寸是靠放大得到的，大屏下会偏软，清单里逐张标注。
- 固定组件库的几何来自真实网页采集，是「固定封装」而非平台全部状态；极简/全屏招牌来自 577px 采样，跨宽度时整体等比缩放。
- 预览是 HTML 页面（483px 真实店铺宽度），可在浏览器里截图保存；**本轮未做服务端 PNG 导出**（避免引入浏览器渲染依赖）。
- 只对一家店做过端到端验证（见下节），不声称已适配所有店铺。

## 七、真实案例实测（2026-10-13）

输入：美妆店铺（可达鸭）商品列表长截图 `1240×9219`（两列网格、约 16 件商品）。

| 项 | 实际结果 |
| --- | --- |
| 终态 | `complete`（无降级项） |
| 总耗时 | 163 秒 |
| 模型调用 | 识别 1 次（1935 in / 836 out tokens）+ 决策 1 次（3969 in / 1928 out tokens）+ 生图 **2 次** |
| 页面 | `483×1432.94px`，7 个模块，10 个图片位，**没有使用任何占位图** |
| 素材 | 11 张：AI 生成 8 张（场景 2 / 图标 4 / 海报 2）+ 截图裁切 3 张 |

AI 的决策（原文摘要）：经典招牌（"简洁横幅更显专业高级"）→ 单行公告 → 四分类导航 → 4:3 中图轮播 → 双列分类海报 → 双列商品橱窗 → 多行售后说明；顺序理由为"先建立大牌感，再做分类引导，随后主推活动与热门商品"。

素材质量（程序记录的客观指标）：

- **残留分隔色全部为 0 像素**（说明裁切没有切到品红）；
- 生成图的裁切丢弃比例：招牌横幅 4.37%，其余 8 张 **0%**；
- 交付像素全部**未放大**（如招牌 1205×558 → 966×448）；
- 3 张商品图来自截图裁切，**放大**后交付（966×725、451×451），因为截图里商品本身较小，清单已逐张标注；
- 生图返回的是 JPEG，已统一转成 PNG 保存。

生图从 1 次变成 2 次的原因（界面已如实说明）：宽幅招牌（483×258 ≈ 1.87:1）与方格格子无法在同一张画布上稳定画对，程序按形状把它单独成图。

## 八、这次实测暴露并修掉的问题

第一次跑并没有一次成功。以下是真实发生的失败与对应修复，都保留在自检里防止回归：

| 现象 | 原因 | 修复 |
| --- | --- | --- |
| 计划被拦下：导航/轮播/海报"给了 0 张图" | 模型把字段写成 `slides` / `items[].icon` / `items[].image`，组件库只认 `images` | 加字段名消歧，把语义明确的变体映射到规范字段 |
| 计划被拦下：橱窗"给了 8 件" | 模块容量是 2/3/6/9，AI 不知道上限 | 按容量裁剪并如实告知（不静默改内容） |
| 计划解析出来是残缺 JSON | 输出超过 `max_output_tokens` 被截断 | 输出上限提到 12000；加保守的截断补全 |
| 橱窗"需要生成但不在生图计划里" | AI 漏写第 9 件的来源 | 商品橱窗槽位一律视为截图裁切（商品图从不生成），不再依赖模型声明 |
| `Missing product price` 渲染失败 | 组件库要求每件商品都有价格字段 | 无可靠价格时给空字符串（页面不显示金额），元数据从渲染内容中剥离，保留在清单里 |
| `EPERM: rename run.json` | 状态文件并发写入冲突 | 状态保存按任务串行化 |
| 裁切"会丢掉 46% 画面" | 宽幅招牌与方格在同一画布，模型统一画成方格 | 按行高跨度分组、按形状拆分画布 |
| 存下来的"PNG"其实是 JPEG | 直接写入了模型返回的字节 | 统一转码为真正的 PNG，并记录返回格式 |

## 十、哪些没测过

已执行的**本地自检全部不调用模型**（`node selfcheck.mjs`）：模块目录与组件库一致、55 个槽位几何自洽、四种典型画布排版合法（尺寸/比例/重叠/越界/宽高比/像素区间）、好计划通过、8 类坏计划被拦下、整页渲染与缺图占位。另外用仓库已有素材做过一次完整页面渲染（`output/sample-render/preview.html`，483×1121px，与共同样例尺寸一致），确认固定模块 + 真实素材能渲染成页面。

**尚未验证**（需要真实调用模型，还没有执行）：

1. AI 对真实店铺截图的识别质量（店名、品类、可见商品框）。
2. AI 选出的模块组合是否真的有理由、适合这家店——这正是本轮要验证的核心问题。
3. 生图模型能否稳定画出「品红分隔 + 无文字 + 比例正确」的组合画布；分隔色检测在真实出图上的通过率。
4. 端到端耗时、失败率与真实费用。
5. 裁切后素材在真实槽位里的观感，以及 2 倍输出是否够用。

界面上的「我确认本次会调用模型」勾选框就是为了这一步：**你确认后我再跑真实案例**，跑完把实际调用次数、耗时、每张素材的来源与质量指标一并报告。
